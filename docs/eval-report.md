# 数码商城智能体评测报告

## 1. 评测口径与资产

| 类别 | 全量题数 | 检索消融题数 |

## 2. 离线检索消融与架构决策

固定题目、语料和切块。两组重排均对 20 个去重候选用同一模型精排，评估 Top 5。混合组以 `tsvector` 匹配归一化后的型号和功率词，用 `pg_trgm` 的 `word_similarity` 匹配短查询与长分块，再与 pgvector 名次做等权 RRF（`k=20`）。

Hit@5 按题统计是否至少命中一个正确分块。Recall@5 按题计算找回的正确分块占该题全部正确分块的比例。MRR@5 取首个正确结果的名次倒数，未命中计 0。三项均按题等权取均值。

| 配置 | Hit@5 | Recall@5 | MRR@5 | 本地检索 P50 | CPU 重排 P50 |
| --- | ---: | ---: | ---: | ---: | ---: |
| pgvector | 56.7% | 48.3% | 0.448 | 8.46 ms | 未启用 |
| pgvector + 重排 | 80.0% | 70.0% | 0.767 | 8.46 ms | 849.28 ms |
| PostgreSQL 混合检索 + 重排 | 93.3% | **86.7%** | **0.883** | 20.86 ms | 889.85 ms |

检索计入查询向量化及数据库查询，混合组还计入关键词检索与 RRF。与同预算的向量加重排相比，Recall@5 提升 **16.7 个百分点**，漏召回率相对下降 **55.6%**，MRR@5 从 **0.767 提升至 0.883**。本地检索 P50 增加约 12.4 ms，沿用现有 PostgreSQL 就能部署，因此本机应用启动器默认启用 `PgHybrid`。

旧表迁移、真实 PostgreSQL 下 Java 检索与 RRF 集成、通道配置和重排回归共 **24 项通过**。启动器可用 `-RetrievalMode Vector` 切回纯向量；部署 Elasticsearch 时可显式选用 `-RetrievalMode Keyword`。[启动配置](../local/Start-StoreAgent.ps1) · [中间件配置](../local/Start-Middleware.ps1)。

## 3. 端到端真实回答

正式评测 **60/60 完整返回，失败 0**。另发出 3 次调试请求（2 次预热、1 次试跑），合计 63 次。调试请求均收到可见正文，旧采集器把原样的 `[DONE]` 当成 JSON 解析，记录为 3 次采集失败。修复解析后完成正式评测，表中指标以正式样本计算。

| 指标 | 实测 |
| --- | ---: |
| 关键事实通过 | 44/50（88.0%） |
| 覆盖全部预标注来源的可点击 URL | 36/50（72.0%） |
| 预期工具路径匹配 | 45/60（75.0%） |
| 首轮追问正确缺失字段 | 4/10（40.0%） |
| 快充高风险案例中，配件标称功率被当成具体配对实测功率 | 0/22 |
| 快充高风险案例中，系列功率范围被套到具体配对 | 1/22 |

事实和引用只计正式作答回合，工具匹配按预标注工具及成功状态计，预期先澄清的回合要求直接追问。快充按案例计数，任一回合越过证据粒度即记一次。

**CL-02**。用户补充“小米 17 Pro + PB2165”后，回答准确区分了充电宝双口合计 165 W 与各口输出，也提到缺少实际协商证据，最终仍声称这组搭配的功率落在 33–120 W。该区间只有系列级证据。针对这一配对，应分别报告配件和手机各自规格、附对应出处，并保留“实际协商功率待核实”的结论。

| 当回合调用次数 | 回合数 | SSE 首事件 P50 | 首条进展 P50 | 首段可见正文 P50 | 首段正文中位 50% 区间 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0–1 次 | 15 | 21.2 ms | 438.1 ms | **1.70 s** | 1.63–2.07 s |
| ≥2 次 | 45 | 21.3 ms | 456.7 ms | **5.57 s** | 4.57–6.89 s |

首事件可为 `meta`，首段正文从客户端发出 SSE 请求起计时。164 次标为工具体耗时的本机商城 MCP 调用 P50 为 **5 ms**，中位 50% 区间为 5–6 ms；该值不含全部工具往返和应用编排。离线 PG 混合检索和 CPU 重排分别为 20.86 ms 和 889.85 ms，来自另一批样本。多工具组首事件与首条进展接近，首段正文更晚，串行模型与工具往返值得优先分段观测。现有数据未分别采集云模型和所有应用环节的跨度，无法量化各段对差值的贡献。[端到端汇总](benchmark/e2e_summary.json)。

## 4. 误差与边界

- **澄清**。每题新开会话，全部案例复用同一评测账号，长期记忆跨题留存。CL-04、CL-07、CL-09 用历史机型填补当前缺失字段。4/10 描述这次带历史记忆的答题表现。冷启动应以独立账号或清空长期记忆后重测，保留同题两轮上下文。产品上将本轮明确确认的机型与历史偏好分开处理，涉及兼容性时优先确认当前机型。
- **出处**。14/50 未达到完整引用要求。其中 8 例事实和预期工具均通过，表现为正文只写来源名称、省略 URL 或给出通用商城入口。另有 CL-06 第 2 回合事实通过、沿用上轮查询而未重新调用，正文也未给可点击 URL。其余 5 例同时未通过事实评分。表现与正文输出格式不稳定相符，现有数据没有定位到统一原因。可在应用层用工具返回的结构化来源生成出处，并单独统计来源确实缺失的情况。
- **工具**。15 个不匹配回合中，9 个是预期只追问却实际调用，包含 3 个依赖账号历史机型的回合。CP-03、CL-05 第 2 回合改用商品查询，事实和引用仍通过；CL-06 第 2 回合沿用同题上轮结果，未发新调用。余下 3 个发生在正式作答且事实未通过，分别为 CP-10 误解目标型号、AS-03 用通用知识检索而漏查售后入口、AS-05 未通过预期工具成功条件且给出不合适的故障处置。精确匹配率衡量与预标注路径的一致性，答案质量另以事实和引用评分判断。

## 5. 复现步骤

使用 Python 3.13、CPU PyTorch 2.8.0、Transformers 4.56.2、psycopg 3.2.12。离线跑测需要一个专用数据库、两个固定修订的模型权重，以及本仓库冻结的题库和语料。

```powershell
docker run -d --name store-benchmark -e POSTGRES_HOST_AUTH_METHOD=trust -e POSTGRES_DB=store_eval -p 127.0.0.1:29432:5432 pgvector/pgvector:pg16
docker exec store-benchmark pg_isready -U postgres -d store_eval
python docs/benchmark/build_dataset.py
python docs/benchmark/run_retrieval.py --models D:/path/to/models --out D:/path/to/results
docker stop store-benchmark
```

按 [本机启动说明](../README.md#本机启动) 启动应用并导入目录后，在本机运行以下命令。复现原口径时复用同一账号。验证冷启动澄清时隔离各题的账号记忆。原始回答保存在本地，公开表保存逐回合评分与计时。

```powershell
python docs/benchmark/run_e2e.py --out D:/path/to/e2e-results
```
